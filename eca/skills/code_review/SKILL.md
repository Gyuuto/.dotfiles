# Code Review

プロジェクト全体、指定ディレクトリ、または指定ファイルのコードをレビューし、改善点と修正点を列挙するスキル。

## Purpose

- コードの品質、可読性、保守性を総合的に評価する
- バグの混入リスク、パフォーマンス問題、セキュリティ問題を特定する
- 具体的な修正提案を優先度付きで提示する
- プロジェクトのコーディング規約（AGENTS.md等）への準拠を確認する

## Trigger

以下のいずれかのケースで実行する:

- プロジェクト全体のコードレビューを依頼された場合
- 特定のディレクトリまたはファイルのレビューを依頼された場合
- リファクタリング前の現状把握を依頼された場合
- コード品質の改善を依頼された場合

## 入力形式

レビュー対象は以下の3つの形式で指定する:

| 形式 | 例 | 説明 |
|------|-----|------|
| 全体 | `.` または省略 | プロジェクト全体 |
| ディレクトリ | `config/` | 指定ディレクトリ以下（再帰） |
| ファイル | `config/settings.py` | 単一ファイル |

指定がない場合はプロジェクト全体をレビューする。

## Steps

### 1. レビュー対象を特定する

- 入力から対象パスを解決する
- 全体指定の場合は `.git` ディレクトリ、`__pycache__`、`.pyc` ファイル、`node_modules` 等を除外する
- ファイル指定の場合はファイルの存在を確認する

### 2. プロジェクトのルールを確認する

- `AGENTS.md` からコーディング規約、命名規則、テスト方針を読み取る
- 言語・フレームワーク固有のベストプラクティスを適用する
- 既存のコードスタイルの一貫性を把握する

### 3. コードを読み込む

- 対象ファイルを読み込み、内容を確認する
- 関連ファイル（インポート元、実装クラス、テスト等）も必要に応じて読む
- ファイルが大きい場合は `limit` を指定してスコープを絞る

### 4. チェックリストに基づいてレビューする

以下の項目を網羅的に確認する:

#### 4.1 機能とロジック
- 意図した動作をしているか
- 境界値・エッジケースを処理しているか
- 無限ループ・デッドロックのリスクがないか
- 予期せぬ入力に対する堅牢性

#### 4.2 エラーハンドリング
- 例外ケースが適切にキャッチされているか
- エラーメッセージが有用か（デバッグに役立つか）
- リソースリークのリスク（ファイルオープン、コネクション等）
- `except Exception:` による過剰なキャッチがないか
- `try/except` の範囲が適切か

#### 4.3 コードスタイルと一貫性
- 命名規則（変数・関数・クラス）がプロジェクト規約に沿っているか
- インデント、クォート、セミコロンの統一性
- ドキュメント文字列（docstring）の有無・内容
- 関数の長さ・複雑度（ cyclomatic complexity の目安）

#### 4.4 設計とアーキテクチャ
- 単一責任の原則に従っているか
- 関数・クラスが適切に分割されているか
- 依存関係が循環していないか
- 抽象化が適切か（過剰・不足でないか）

#### 4.5 パフォーマンス
- 不必要なループ・処理の重複がないか
- 大きなデータ構造の不要なコピーがないか
- I/O 操作が最適化されているか（バッチ化、キャッシュ等）
- 非同期処理の適切な使用

#### 4.6 セキュリティ
- 機密情報（APIキー、パスワード、トークン）のハードコーディング
- SQLインジェクション、XSS等の脆弱性
- 入力値の検証・サニタイズ
- 機密ファイル（`.env`、認証情報）のリポジトリ混入

#### 4.7 テスト
- 対応するテストファイルが存在するか
- テストが AGENTS.md のテスト方針に従っているか
- テストファイルが `tests/` ディレクトリに配置されているか

#### 4.8 ドキュメント
- コードに適切なコメント・docstring が付いているか
- 外部公開される値（IPアドレス、APIエンドポイント等）が漏れていないか
- プロンプトファイル（AGENTS.md、SKILL.md等）とコードの整合性

### 5. 問題点を分類・優先度付けする

優先度分類:

| 優先度 | 意味 |
| --- | --- |
| `blocker` | 修正必須。機能しない、データ損失のリスク、セキュリティ脆弱性 |
| `major` | 修正推奨。実害が発生する可能性、保守性の重大な低下 |
| `minor` | 改善提案。品質向上のため推奨、コードスタイルの不一致 |
| `info` | 参考情報。ベストプラクティス、オプションの改善 |

### 6. レポートを生成する

- 問題点をファイルパス・行数付きでリスト化
- 各問題に具体的な修正案を付与
- 全体評価と所見を記載

## Output

レビュー結果を以下の形式でレポートする。

```markdown
## レビュー結果

### 概要
- レビュー対象: [プロジェクト全体 / ディレクトリパス / ファイルパス]
- レビュー対象ファイル数: N
- 総行数: N

### 全体評価
[変更の概要と品質を簡潔に評価。1〜2文]

### 問題点一覧

#### [blocker/major/minor/info] 問題の要約
- 該当箇所: `ファイルパス:行数`
- 優先度: `blocker` / `major` / `minor` / `info`
- 説明: 問題の具体的な内容
- 提案: 修正案または改善方法

### 改善提案
[網羅的な改善ポイントを列挙。優先度順]

### 所見
[自由記述。全体を通した所感、アーキテクチャ的な観察、次回レビューの推奨時期など]
```

### 出力ルール

- 各問題点は独立したセクションとして記述する
- 該当箇所はファイルパスと行数を明記する
- 提案は具体的で実行可能な内容とする
- 全項目に問題がない場合は「該当なし」と明記する
- 全体評価は1〜2文で簡潔にまとめる
- 優先度 `info` のみ「該当なし」は省略可
- ファイルが大きい場合は、レビューした範囲を記載する

## 注意事項

- ファイルの読み込みには `eca__read_file` を使用し、`original_content` は正確にコピーする
- 大規模プロジェクトの場合は、対象ディレクトリを限定してレビューする
- 既存のスキル（`diff_review`）と使い分ける:
  - `diff_review`: 変更差分のレビュー（既存コードとの比較）
  - `code_review`: 既存コードの総合的な品質レビュー
